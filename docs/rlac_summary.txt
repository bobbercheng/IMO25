  Verifier:  "INVALID - Multiple critical errors" ✗ FAILS VERIFICATION

Gap Analysis:

  • Mathematical language is appropriate
  • Reasoning flow appears logical
  • BUT: Theorem preconditions not actually satisfied
  • BUT: Claims (CE = AE) false without justification

  Generator confidence: "This is rigorous" (99%)
  Verification confidence: "This has critical errors" (99%)
  Gap: No mechanism during generation to challenge weak assumptions

PROPOSED ENHANCEMENTS (6 Key Improvements):
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. CRITIC-ASSISTED SOLUTION GENERATION (CASG)
   Current: Generate full solution → Verify at the end
   Proposed: Outline → Critic attacks → Generator revises → Full writeup
   
   Benefit: Early detection of doomed approaches
   Timing: During generation, not after
   Cost: Early rounds cheap (outline only), not full proof

2. STRUCTURED FLAW REPORTING WITH SEVERITY & LOCATION
   Current: "Verdict: BROKEN"
   Proposed: JSON with type/severity/location/claim/why_wrong/counterexample/fix
   
   Example fix for "CE = AE" error:
   {
     "type": "logical_error",
     "severity": "critical",
     "location": "Step 4: Chord Identification",
     "specific_claim": "chord CE coincides with chord AE",
     "why_wrong": "Points C, A, E are not collinear (C and A distinct on Ω, 
                   E is second intersection of line AP with Ω)",
     "counterexample": "In configuration with Ω centered at origin, radius 1,
                        C and A are distinct points on Ω, E on different arc",
     "suggested_fix": "Use power-of-a-point instead: AC·AD = AB² = AE·AF"
   }
   
   Benefit: Generator can target specific fixes, not redo entire solution

3. GEOMETRY-SPECIFIC ATTACK CURRICULUM
   Current: Generic BASIC → MODERATE → ADVANCED
   Proposed: Domain progression optimized for geometry
   
   Round 0-1: Definition Check
     "Does every term used exist? Is point P on line L?"
   Round 2-3: Theorem Preconditions
     "Angle-bisector applies: verify vertex, angle, opposite side"
   Round 4-6: Configuration Verification
     "Can you construct this explicitly? Is it non-degenerate?"
   Round 7-8: Logical Closure
     "Are all cases covered? Circular reasoning?"
   Round 9+: Rigorous Reconstruction
     "Rewrite formally with every step justified"
   
   Benefit: Attacks match problem complexity, not generic difficulty

4. COUNTEREXAMPLE GENERATION FOR GEOMETRIC CLAIMS
   Current: Attack identifies issues, maybe with examples
   Proposed: Systematic construction of configurations breaking claims
   
   For "∠CEA = ∠DFA":
     Construct explicit circles Ω, Γ with centers M, N
     Find points A, C, D, E, F explicitly
     Compute actual angles: ∠CEA = X°, ∠DFA = Y°
     If X ≠ Y: Counterexample found
   
   Benefit: Generator sees EXACTLY why claim fails, not abstract criticism

5. DEFENSE & CONCESSION TRACKING
   Current: Generator receives verdict, has to infer what to fix
   Proposed: Track how generator responds to each attack
   
   Response Type A (Valid Defense):
     Generator: "AP ⊥ PM because [PROOF]. Your attack misunderstood."
     Analyzer: Critic attack was spurious, improve critic
   
   Response Type B (Concession):
     Generator: "You're right, AP ⊥ PM is unjustified. Let me fix it."
     Analyzer: Generator learned correct response to this attack type
   
   Response Type C (Deflection):
     Generator: "That's minor, main argument still holds..."
     Analyzer: Red flag - generator avoiding the issue
   
   Benefit: Identifies which attacks work and which don't, improves critic

6. CONFIDENCE CALIBRATION THROUGH ADVERSARIAL FEEDBACK
   Current: No confidence tracking; generator is overconfident
   Proposed: Force confidence statements + penalties for miscalibration
   
   Before attack: Generator states "I claim [X] with confidence 0.95"
   After attack: 
     If claim holds → Confidence justified, reward
     If claim breaks → Miscalibration penalty (larger than normal error penalty)
   
   Learning signal: Overconfident incorrect claims are worse than 
                    careful partial claims
   
   Benefit: Solutions become better calibrated to actual difficulty

MULTI-STAGE VERIFICATION PIPELINE:
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Instead of single binary verification at the end:

Stage 1: Outline Verification (EARLY)
  → Is strategic approach sound?
  → Are lemmas correctly stated?
  → Does flow make sense?
  → Kill doomed approaches early

Stage 2: Lemma Verification (MID)
  → Each lemma attacked as standalone theorem
  → Preconditions stated?
  → Proof complete?
  → Counterexample exists?

Stage 3: Integration Verification (LATE)
  → Do lemmas connect?
  → Does final claim follow?
  → Circular dependencies?

Stage 4: Robustness Verification (FINAL)
  → Remove one assumption—still true?
  → Boundary cases handled?
  → Can rewrite formally?

Each stage → specific criticisms → feedback to generator

KEY INSIGHT: TIMING MATTERS MORE THAN QUALITY
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

Current: Excellent critic, wrong time
  Generate full solution (overcommitted to approach)
  → Run verification (critical errors found)
  → Too late to reshape generation process

Proposed: Good critic, right time
  Generate outline (low commitment)
  → Run critic (attacks weak claims early)
  → Generator has time to try alternative approach
  → Iteratively improve while generation is still flexible

Result: Solutions shaped by adversarial feedback during generation,
        not judged by verification after completion.

RESEARCH CONCLUSION:
━━━━━━━━━━━━━━━━━

The IMO-02 test case reveals a fundamental gap: **fast generation (low reasoning) 
produces solutions that SOUND good but are ACTUALLY invalid**.

This gap is NOT fixed by:
  ✗ Better verification (it catches errors too late)
  ✗ Higher reasoning effort (too expensive during generation)
  ✗ More training data (doesn't teach calibration)

This gap IS fixed by:
  ✓ Inserting adversarial critics DURING generation (not just after)
  ✓ Providing SPECIFIC feedback (structured flaws with location, not binary verdict)
  ✓ Using DOMAIN-SPECIFIC attacks (geometry patterns, theorem preconditions)
  ✓ TRACKING generator responses (defense vs. concession learning)
  ✓ CALIBRATING confidence (penalize overconfidence, reward justified claims)

RLAC framework provides exactly this: An adversarial critic that acts as a 
"PROOF SABOTEUR" rather than a "PROOF GRADER", enabling feedback to shape 
generation, not just judge it.

By shifting WHEN and HOW criticism is applied, we can move from:
  Current: Overconfident invalid solutions
  Target: Calibrated, verification-resistant solutions

The proposed enhancements are research-ready and can be implemented 
incrementally into the existing codebase.
